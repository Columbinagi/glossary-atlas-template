# 生成术语卡片

输入：一个术语（可带一句方向说明，如「偏工程视角」「和工业电机对比着写」）。
输出：`content/草稿/<id>.md` —— 一张合规卡片，等人审阅。**不收录、不构建、不分配正式编号。**

## 先读这三份（不要凭记忆写格式）

1. `content/内容规范.md` §3 字段契约、§4 写作纪律、§5 编号规则。
2. `content/知识库/电驱与电机/120-pmsm.md` —— **格式范本**，逐节的写法照它。
3. 要配图再看 `content/知识库/电驱与电机/100-edrive-system.md`（积木图）与 `120-pmsm.md`（内联 SVG）两种范式。

## 卡片骨架（节标题、顺序、标记一律照抄；没有内容的整节省略，不要写「待补」）

```
## 000. 词条名                      ← 编号固定写 000 占位，正式编号由收录脚本分配

- id: `kebab-case-英文id`
- 主题: `t5`                        ← 或 - 分类: `c2`（二者至少要有一个，见 站点配置.js）
- 英文名: English Name

### 你可能会说                      → 引用块，一句使用者会脱口而出的话
### 是什么                          → 一句总起句，说清是什么（必填）
### 详解                            → 短横线列表 2–3 条：划边界、举例
### 先知道                          → 名称（见 [[词条id]]）  或  纯文字概念
### 别名                            → 顿号分隔
### 图解                            → html 代码块（积木图或内联 SVG）
### 一句话                          → 图下那句结论
### 演示注解                        → 图的小字说明
### 主线位置                        → 当前: N ／ 标题: … ／ 说明: … ／ 再列 1. 2. 3. 步骤
### 组成结构                        → html 舞台图代码块 + 部件行「1. 名称（En）：说明」
### 可操作演示                      → json 代码块（状态机，可选）
### 正文分点                        → #### 小标题 + 段落（2–3 个小节，讲「为什么」）
### 使用场景                        → **什么时候用** ／ **什么时候不用** + 条目 + html mock
### 常见变体                        → - **名称**（En）：说明 + html mock
### 容易混淆                        → - vs **X**：差在哪
### 选择题                          → 题干 ／ - A. … ／ 答案: B ／ 解析: …
### 告诉 AI                         → 一段可直接复制的提问模板
### 接下来学什么                    → - [[词条id]] —— 说明（只能指向**已存在**的词条）
### 来源                            → - 名称：https://…（全角冒号，否则 URL 会被丢掉）
```

写代码块时照抄现成卡片的写法：`### 图解` 与 `### 组成结构` 用 html 代码块，`### 可操作演示` 用 json 代码块，`### 使用场景`／`### 常见变体` 的 mock 用 html 代码块。

## 写作纪律（长期有效，逐条对照）

- **时间锚点**：数据类表述必须带时间（如「截至 2026 年上半年」），并在 `来源` 标注；概念类可长期使用。**查不到就写「未公开」，不要用行业平均值补位。**
- **比较三件事**：凡「A 比 B 强多少」，必须同时交代**分母口径、工况（峰值/持续）、产品阶段（原型/量产）**；三项不同就声明「不可直接比较」。
- **学理优先**：解释「为什么」，不罗列「是什么」，不写成参数表。
- **不写投资建议**，不预测股价与销量排名。
- **客观中立，不预设读者身份**（2026-09-22 定，取代更早的「优先工业对比视角」）：与工业电机、工业变频器等相邻领域的对照**可以有**，但要**从简、中立、以事实陈述的方式写**，不能成为每张卡片的固定栏目，更不能出现「你们厂」「你的本行」「厂里」这类指向使用者身份的措辞。
- **信息准确性由撰写方负责**（2026-09-22 定）：取源优先级 **标准原文 / 官方发布 > 第三方机构 > 行业媒体**；查不到权威出处就写「未公开」。引用的数字要能在 `来源` 里指到具体出处与时间。

## 配图规则

- **流程、分层、状态、卡片式对比** → 原生积木：`dk-flow` / `dk-stage` / `dk-arr` / `dk-status` / `dk-cols`；拟真界面用 `mk-*`（`mk-row` / `mk-tag` / `mk-alert` / `mk-spinner`）。
- **物理结构**（电机剖面、电池包、充电曲线等积木画不了的） → **内联 SVG**：`viewBox="0 0 400 225"`（单图）或 `"0 0 640 400"`（剖面），带 `role="img"` 与中文 `aria-label`。
- 颜色**一律用 CSS 变量**（`var(--brand)` / `var(--text-2)` / `var(--bg-soft)` / `var(--orange)` / `var(--red)` / `var(--gray-4)` …），这样明暗主题自适应；写死色值会在暗色下掉色。
- 每张卡最多一张主图（`### 图解`）+ 一张舞台图（`### 组成结构`，可选）。

## 格式红线

1. **`### 来源` 的名称与 URL 之间必须是全角「：」**——写成半角 `: ` 时解析器不认，URL 会被整段丢掉。
2. **`### 先知道` 的互链必须写成「名称（见 [[词条id]]）」**——括号与「见」都是全角。写成 `(see [[id]])` 不生效。
3. **`### 组成结构` 部件行用全角「：」**：`1. Inverter（Inverter）：converts DC into…`。
4. 正文强调**只用「」或互链**，不要用 Markdown 加粗（`**x**` 会原样显示星号）。契约标记（`**什么时候用**`、`- **名称**`）除外，它们必须原样写。
5. `id` 只允许小写字母、数字、连字符；`id` 与 `[[互链]]` 里的 id 必须完全一致。

## 常见警告（校验的及格线是 0 错误 · **0 警告**，下列每条都会卡住收录）

- **`### 一句话` / `### 演示注解` 必须有 `### 图解` 配对**——只有结论句、没有图，会各报一条警告。图省事时就把这两节一起省掉。
- **`### 组成结构`**：舞台图代码块与部件行**必须成对**；部件行序号要与舞台图里 `data-ap` 一一对应，不能有单边多出来的。
- **`### 主线位置`**：步骤数保持 3–7 步，每步都要有文字。
- **`### 选择题`**：`答案:` 与 `解析:` 都要有（缺解析会警告）。
- **`### 正文分点`**：每个 `####` 小节下面必须有段落，不能只有标题。
- **`### 使用场景` / `### 常见变体` / `### 容易混淆`**：条目不能只有壳（缺 text / 缺说明 / 缺 say 都会警告）。
- **`- 主题:` 与 `- 分类:` 别同时写得不一致**——引擎按 `分类` 推导主题，两者冲突会警告。不确定就只写一个。
- **`接下来学什么`**：不要指向自己；每一项都要有 id。

## 交稿前自检（必跑）

```bash
node engineering/收录草稿.mjs content/草稿/<你的文件名>.md --dry
```

这条命令用**正式解析器**读你的卡片，并预演收录位置（--dry 不改任何文件）。必须看到「收录：content/知识库/<主题>/<编号>-<id>.md（编号 …，排在…）」；若报「草稿校验未通过」，按报错改卡片，**不要绕过、不要改脚本**。

## 不要做

- 不要写 `content/知识库/`（草稿区才是你的写入点），不要改 `engineering/`，不要跑 `拼合.mjs`。
- 不要自己填正式编号、不要删改别的卡片、不要顺手「优化」已有内容。
- 不要替用户判定「可以收录了」——收录是下一个技能 `term-card-publish` 的事，且必须由人确认。

## 交稿话术

一句话说清：卡片落在哪、id 是什么、预演编号是多少、哪几处数据带了时间锚点、哪几项标了「未公开」。

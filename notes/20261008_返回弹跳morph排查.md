# 20261008 返回弹跳（morph 起点跑到画外）排查

> **类**：分析 / 论证（**只增不改**）。触发：使用者 2026-10-08 报障。
> 结论索引在 `MEMORY.md` §2；骨架变更登记在 `CHANGELOG.md` 续 14；验收基准新增 V10（见 `PRD.md` §六 与 `ACCEPTANCE.md`）。
> 过程取证（5 个探针脚本、逐帧截图、净室副本路径）在 `logs/morph-返回弹跳复现/`（**不进版本库**）。

## 一、报障原文与判定

使用者原话：「点开一张卡片并往下滑到一定程度，再点返回，这个卡片会从上方不知道哪个地方——反正很高的地方——一下子弹到原本的位置」。

判定：**不是错觉，是引擎的真缺陷**，100% 稳定复现；缺陷在 `renderApp()` 的「详情 → 列表」分支，**与内容无关**（母版自带示例数据即可复现）。

## 二、怎么量的（方法与为什么这么选）

- 要量的东西：morph 副本在**每一帧**的视口位置。
- 关键事实：Chrome 里 `::view-transition-group(morph)` 的 `transform` **就是该副本在视口里的绝对坐标**（`matrix(1,0,0,1,x,y)`；x 是列偏移、y 是视口 y）。于是 `getComputedStyle(document.documentElement,'::view-transition-group(morph)')` 可以逐帧采样——本机 Chrome 154 实测可读，没有 morph 时返回 `none`。
- 采样用**页面内 `requestAnimationFrame` 循环**（不是 CDP 往返），避免 RPC 延迟污染时间轴；驱动与截图走 CDP（Node 内置 `WebSocket` + `fetch`，**零 npm 依赖**）。
- 五个探针（`logs/morph-返回弹跳复现/`）：

| 文件 | 作用 |
|---|---|
| `probe.mjs` | 首轮复现：把过渡放慢到 4s，逐帧截图 + 几何 |
| `probe2.mjs` | **7 档滚动扫描** —— 给出「起点 ≡ hero 视口 y」这条决定性证据 |
| `probe3.mjs` | 真实速度 vs 只放慢 morph 的逐帧截图（视觉取证） |
| `probe4.mjs` | **四段对照**（打开卡片 / 浅滚返回 / 深滚返回 / 浏览器后退键），改前改后各一轮 |
| `probe5.mjs` | 量「继续上次」横幅高度与落点 55px 差 |

## 三、实测数据

1280×800 / Chrome 154，母版自带示例数据，点列表第一张卡；在详情页滚到目标位置后点「← 返回」：

| 详情页下滚 | hero 在视口 | morph 起点 y | 终点 y | 位移 | 采样区间 |
|---|---|---|---|---|---|
| 0px | 231 | 231 | 294 | 63px | 45–519ms |
| 150px | 81 | 81 | 294 | 213px | 40–517ms |
| 300px | −69 | −69 | 294 | 363px | 58–514ms |
| 600px | −369（已出视口） | −369 | 294 | 663px | 56–501ms |
| 1000px | −769 | −769 | 294 | 1063px | 54–516ms |
| 1800px | −1569 | −1569 | 294 | **1863px** | 46–491ms |
| 2744px（滚到底） | −2513 | −2513 | 294 | **2807px** | 49–513ms |

**第 3、4 列 7 档完全相等**：morph 起点就是 hero 当时的视口 y。

真实速度（不减速）时间线：返回后 **~139ms 副本仍在视口上方 368px 处**、~266ms 已冲到 y=212、~374ms 落位 294 —— 近 1900px 的位移有一大半在 100ms 出头走完。

## 四、根因链

1. `renderApp()` 的「详情 → 列表」分支**无条件**把 `#detail-hero` 挂成 morph 起点（母版 `:4697` 一带；搜 `toList && savedCardId` 最稳）。
2. 视图过渡的 morph = 「旧元素**此刻**的视口方框 → 新元素方框」的补间；而 `paint()` 在返回时把列表恢复到 `savedScrollY`，卡片落在 y≈294。**起点与终点各自取自不同时刻的布局**，这是位移被放大的结构性原因。
3. 于是位移 = 卡片落点 − hero 当前视口 y = 常数 + **详情页的滚动量**。

- **为什么"滑到一定程度"才出现**：hero 在页首 y=231、高 271px ⇒ 滚过约 231px 它顶边就出视口，再往下滚起点就跑到画外。
- **为什么"一下子"**：`.45s` 的 `cubic-bezier(.22,1,.36,1)`（强 ease-out）——大部分路程在前 1/3 时间内走完。

## 五、它是「漏了一处」，不是新问题类

`across`（详情 → 上/下一条）分支早就写了守卫：

```js
if (across && (window.scrollY || window.pageYOffset || 0) > 240) vtSkip = true;
```

其注释写明原因正是同一个根因：「两张快照的垂直差被一并补间，叠加原本设计的水平滑动，就成了所报的『斜向』过渡」。**返回列表这条路径没有对应守卫** —— 本轮补上。

## 六、修复方案与对照

**采用的（使用者拍板「紧判据」）**：新增 `morphSourceOnScreen()`（母版 `:4581`，**搜符号最稳**）——hero 顶边仍在视口内，才认为 morph 起点可信；不满足时**不挂 morph 名**，退化为页面级淡入（引擎里既有的退化路径，与「morph 找不到目标自动退化为淡入」同一条）。落地改动 2 处：新增该函数 + 「详情 → 列表」分支加条件（`:4697`），另同步 `renderApp` 顶部「三个场景」注释。

四段对照（同一套探针，改前 / 改后）：

| 场景 | 改前 | 改后 |
|---|---|---|
| 打开卡片（列表→详情） | morph 239→231 | morph 239→231（**不变**） |
| 返回，详情未滚 | morph 231→294 | morph 231→294（**不变**） |
| 返回，详情滚到底 | morph −1569→294（1863px） | **不 morph，改淡入** |
| 同上，落地结果 | scrollY=0，卡片 y=293.7 | scrollY=0，卡片 y=293.7（**不变**） |
| 浏览器后退键（深滚） | morph 231→294 | morph 231→294（**不变**） |

**未采用的备选**（留档，勿重复讨论）：

1. **松判据**（hero 只要还有任意一部分可见就保留 morph）：边界处仍有明显"从上滑下来"——实测 300px 档位移 363px、600px 档 663px，hero 底边刚出视口时位移约 565px。
2. **返回前先把详情页滚回顶部再做 morph**（让页面内返回键与浏览器后退键看齐）：morph 全保留、位移恒为 63px；代价是旧快照变成文章顶部，等于用「假装你在顶部」换动画；而且浏览器后退键的真实机制是「恢复到目标历史条目的滚动位置」（不一定是顶部），并不真的等价。
3. **纯 CSS 修**：做不到。位移来自 UA 生成的关键帧，作者只能改时长 / 缓动，改不了起点方框。

## 七、闸门（防止回退）

`校验.mjs` ③-d（`headlessMorphGate`）：

- 判据**不依赖动画时序**——只看 `startViewTransition` 被调用那一刻谁挂着 `view-transition-name="morph"`（无头 + 虚拟时间下 VT 回调本就不保证触发，引擎里有 250ms 兜底，见其注释）：
  **A** 列表→详情 = 被点的那张卡片；**B** 详情未滚时返回 = `#detail-hero`；**C** 详情滚到底返回 = **没有任何元素**，且滚动与落点跟点开前一致。
- 跑**母版**而不是产物：引擎逐字节随拼合进产物（拼合按 `MARK_ENG` 切），而母版自带长示例数据、能稳定构造「滚到底」；净室起步只写一张短示例卡，构造不出来 —— 那种情况报 ⏸（需外部验证）而不是假绿。
- **红绿双向验证**：改前判红 `C=#detail-hero（hero 在视口 y=-3767）`；改后判绿 `A=card:doc-online；B=#detail-hero；C=none（落点 285→285，scrollY 0→0）`。

## 八、顺带实测到的两件事（都未处理，留证）

1. **「继续上次」横幅带来的 55px 落点差**：返回时该横幅才第一次出现（实测高 **55px**），而滚动是按键 `scrollY` 恢复的 ⇒ 卡片落点比点开时低 55px（实测 238.7 → 293.7）。**一次性、不是动画**。口径上属既有取舍：v5 曾把"恢复卡片在视口里的位置"改成"恢复 scrollY"（见母版里 `savedScrollY` 处的注释）。
2. **入口不对称**：页面内「← 返回」按钮与 Esc 走有缺陷的路径；**浏览器后退键不会** —— 浏览器先把滚动恢复到目标历史条目，快照在那之后才拍（采样见证：后退键那一路 `t=1ms` 时 scrollY 还是 1800、`t=22ms` 已是 0，而过渡起点 y=231）。修复后：前者深滚改淡入，后者仍保留 63px 的 morph。
